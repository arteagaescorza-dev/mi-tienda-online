CÓDIGO OFICIAL DE REGLAS DEL PROYECTO

Compendio normativo de arquitectura fullstack, directrices de base de datos, aislamiento DOM, sincronización multiverso y estándares de calidad para el ecosistema Mi Tienda Online.

1. Vertical Slice Senior (End-to-End)

Cero datos mockeados o interfaces cosméticas. Toda funcionalidad persiste en MySQL, modelos Eloquent, FormRequests y pruebas PHPUnit.

2. Single Inventory Pool Desacoplado

Un almacén central (Hub 4 Kardex) abastece cuatro vitrinas independientes (Marte, Venus, Tiresias, Terra) con reglas taxonómicas.

3. Aislamiento Estructural de Paneles y Modales

Los 6 paneles y 7 modales operativos CMS residen como nodos hermanos bajo #storeAppRoot (depth=2), erradicando bloqueos por CSS.

4. Workflows de Aplicación sin Roles

La documentación modela cómo se interconectan los datos entre módulos, sin mezclarse con perfiles o descripciones de puestos laborales.

Proyecto: Mi Tienda Online (PWA RevOps)
Alcance: Hubs 1 al 7 + Storefront D2C
Vigencia: Normativa Obligatoria 2026
Estatus: Activo / Mandatorio
Compilación: Tríptico Documental (MD + HTML + PDF)
Versión: Canon v2.4

1. PRINCIPIOS FUNDAMENTALES DE INGENIERÍA Norma 1.0

1
Regla 1.1: Metodología Fullstack Senior (Vertical Slice) Queda estrictamente prohibido el desarrollo de interfaces cosméticas o "mockeadas" sin persistencia real. Toda tarea debe entregarse con persistencia en MySQL, modelos Eloquent con relaciones, validación en FormRequests, controladores RESTful/Blade, vistas interactivas PWA y batería de pruebas PHPUnit automatizadas.
MySQL (DDL) ➔ Eloquent ➔ Servicios ACID (Kardex) ➔ Endpoints REST ➔ UI PWA ➔ PHPUnit Tests
2
Regla 1.2: Integridad del Código Existente y Comentarios Preservar rigurosamente los comentarios, docstrings e implementaciones previas. Ninguna refactorización debe romper submódulos adyacentes ni alterar contratos existentes sin previa validación en pruebas de regresión.
3
Regla 1.3: Sincronización Mandatoria con BACKEND_INTEGRATION_SPEC.md Ninguna tarea se considera "Completada" si sus tablas, columnas, esquemas JSON y FormRequests no están 100% formalizados de antemano en el contrato de backend maestro.

3. REGLAS DE ESTRUCTURA DOM, BLADE & AISLAMIENTO DE MODALES Norma 3.0

1
Regla 3.1: Aislamiento Estructural de Paneles y Modales (Regla Anti-Anidamiento) Todos los paneles de pestañas (.tab-panel) y todos los modales interactivos (#createSectionModal, #editSectionModal, #editSizeGuideModal, etc.) deben ser hermanos directos e independientes en el nivel depth = 2 bajo #storeAppRoot.
Peligro Crítico: Nunca anidar un modal dentro de un panel con clase tab-panel hidden. La regla .tab-panel.hidden { display: none !important; } anula cualquier fixed inset-0 z-50, tornando el modal invisible e inerte al clic del usuario.
2
Regla 3.2: Balance Matemático y Cierre Estricto de Etiquetas Blade Toda vista Blade debe mantener paridad absoluta entre aperturas y cierres de <div>. Cada sección de acordeón debe cerrar explícitamente su body y su contenedor principal antes de iniciar la sección siguiente.
3
Regla 3.3: Limpieza y Control de Estilos en Apertura de Modales Toda apertura de modal debe remover la propiedad inline (modal.style.removeProperty('display')) antes de asignar display: flex, e invocar el modo por defecto (Catálogo) para evitar estados corruptos.

4. REGLAS DE INTERFAZ, CSS & STOREFRONT PWA Norma 4.0

1
Regla 4.1: Sangrado de Pantalla Completa (Full-Width Breakout) Los Hero banners pueden expandirse al 100% del viewport (width: 100vw; margin-left: -50vw; left: 50%;) sin desbordes horizontales, aplicando overflow-x: hidden en el layout raíz.
2
Regla 4.2: Cache Busting Dinámico Obligatorio Todo activo crítico de estilos o scripts debe inyectar versionamiento dinámico basado en la fecha de modificación: ?v={{ filemtime(...) }}. Esto garantiza que las correcciones móviles y de PWA se reflejen de inmediato sin exigir vaciado de caché al cliente.
3
Regla 4.3: Ergonomía de Navegación (Cero Scroll Horizontal) Las subnavegaciones se ordenan en cuadrículas estructuradas (ej. 2 filas de 3 columnas). El conmutador de vitrinas (.universe-selector-bar) debe permanecer visible y persistente en todas las pestañas.
4
Regla 4.4: Restricción Estricta de Cajas de Texto (Solo Expansión Vertical) Ninguna caja de texto (<textarea>, input multilínea o editor de código) puede expandirse de forma horizontal en ninguna pantalla o formulario del sistema. Queda terminantemente prohibido el uso de resize: both o resize: horizontal. Toda área de texto aplica obligatoriamente resize: vertical !important; max-width: 100% !important; box-sizing: border-box !important; para salvaguardar las cuadrículas y prevenir scroll horizontal parásito.

5. MERCHANDISING, CMS & SECCIONES MODULARES (HUB 2) Norma 5.0

Tipo de Sección Características Permitidas Restricciones Estrictas
Catálogo de Prendas (Tarjetas, Categorías, Familias, Tags) Filtros dinámicos Hub 4, marcas, límite de prendas, layouts en cuadrícula o carrusel. Prohibido código custom: Cero HTML, CSS o JS libre para proteger integridad del catálogo.
Contenido & Hero (Hero, Banners, Pilares, Modales, CTA) Bifurcación excluyente (visual vs código), degradados overlay, imagen de fondo, código scoped. Sanitización en backend obligatoria: Todo input HTML/JS se purifica antes de persistir.
Gestor Drag & Drop (Secciones del Home) Reordenamiento en vivo, activación/pausa, archivado atómico, asignación de vitrina. Confinado a Tab 1: Exclusivo del Editor Visual; no aparece en las demás pestañas.

6. SEGURIDAD, CALIDAD & DOCUMENTACIÓN VIVA Norma 6.0

1
Regla 6.1: Cero Tests Rotos (100% Passing Test Suite) Ningún commit se consolida si la suite de pruebas PHPUnit presenta un solo error o fallo. Todas las aserciones deben reportar estado verde.
2
Regla 6.2: Validación en Navegador Real con Chrome DevTools Protocol (CDP Headless) Incidentes visuales o reactivos se diagnostican inspeccionando dimensiones reales (offsetHeight, offsetWidth) y la cadena de ancestros (modalParentChain) en Chrome Headless.
3
Regla 6.3: La Regla del Tríptico Documental Toda directriz arquitectónica o manual de flujos debe sincronizarse en tres formatos simultáneos: Markdown (*.md) ➔ HTML Editorial (*.html) ➔ PDF Imprimible (*.pdf vía Chrome).
4
Regla 6.4: Registro Continuo en PENDING_TASKS.md & Commits Semánticos Toda oportunidad o bug se registra formalmente con ID TASK-XXX-NN. Los commits de Git declaran de manera atómica el ID de tarea y la naturaleza de la solución (feat:, fix:, docs:).
Vigencia y Mandato: Este código de reglas es de observancia obligatoria para cualquier agente, desarrollador o mantenedor del repositorio Mi Tienda Online. Cualquier desviación técnica debe ser corregida de inmediato para preservar la estabilidad, escalabilidad y excelencia operativa de la plataforma.
